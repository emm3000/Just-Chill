# CI, release and the gate

- `./gradlew qualityGate` is the gate, invoked by the three build workflows (`buildDev`, `uploadApk`, `uploadRelease`; `probeStorageRls` runs no Gradle). Its task list lives in `build-logic/.../QualityGateConventionPlugin.kt` and is pinned by `ConventionPluginTest`'s `AGGREGATE_GATE_TASKS` / `NAMED_GATE_TASKS`; read those constants, never a prose copy, and change them in the commit that changes the plugin. What the code cannot show: task-name matching never reaches an included build, so `:build-logic:convention:test` is named explicitly, as are `:androidApp`'s flavored test and lint tasks, because its flavors live in its own build file; `compileReleaseKotlin` is named because dropping `detektRelease` dropped the only thing that type-checked a library module's release variant; `:androidApp` is exempt from `checkComposeFreeViewModels` as the composition point; `qualityGate { detektTasks }` replaces the aggregates so each source set is covered exactly once. Never gate on plain `./gradlew detekt`: it covers strictly less.
- Triggers. `buildDev` (PR to `trunk`): a `changes` job runs `git diff --name-only` against the base; the required check `quality-gate` is skipped (counted as passing) only when the PR touches `**/*.md`, `docs/**`, `.claude/**`, `scripts/justchill-*` or `.github/dependabot.yml` alone, and runs whenever `changes` did not succeed. It runs `qualityGate :androidApp:compileProdReleaseKotlin`, plus `assembleProdRelease` only when the PR touches a keep-rule file (`*.pro`) or `build-logic/convention/src/main/kotlin/com/emm/buildlogic/AndroidReleaseConventionPlugin.kt`. Everything else that can break the release — an AGP or R8 bump in `gradle/libs.versions.toml`, a `consumerProguardFiles` wiring in a library module, the prod flavor's own signing line in `androidApp/build.gradle.kts` — is caught by no R8 run at all until a dispatch or a release tag, because `trunk` stopped building while the migration runs. A PR's R8 run never protected on-device data, since the enum keep rules the app relies on are already absent and `assembleProdRelease` stays green when a keep rule points at a package that no longer exists. `uploadApk` (every `trunk` push): the full gate plus `:androidApp:compileProdReleaseKotlin`, and nothing else; a newer push cancels the running one. Its two builds and both Firebase App Distribution steps are `workflow_dispatch` only while the ADR 015 migration runs, so a trunk push no longer produces an APK and the build for the device is requested by hand. R8, resource shrinking and release lint therefore run on a PR that touches the release wiring, on a dispatch, and on `uploadRelease`, nowhere else. Restore the push-triggered builds when the migration lands. `uploadRelease` (tag `v*.*.*` or manual): gate, release lint, bundle, Play draft. Report upload paths are `**` globs, never module names.
- Branch protection is `strict: false`, so the `uploadApk` gate is the only net for semantic conflicts between PRs green on their own. Never drop it — dropping its *builds* is what the migration did, and that is not the same thing.
- The Crashlytics mapping upload runs only with `-Pjustchill.crashlyticsMappingUpload=true`, which `uploadApk` passes on `trunk` and `uploadRelease` on a release tag or a manual dispatch from `trunk`. PRs, Dependabot and local builds never upload.
- Caching. `uploadApk` on `trunk` is the only writer; `buildDev` and `uploadRelease` pass `cache-read-only: 'true'`. `uploadRelease` is read-only because it runs on a `v*.*.*` tag ref and GitHub scopes a cache entry written there to that tag, so no later run can restore it — writing only burns the repo's 10 GB budget. The configuration cache is persisted only when the `GRADLE_ENCRYPTION_KEY` secret is set: without `cache-encryption-key`, setup-gradle saves and restores no configuration-cache data at all and every run recalculates the task graph. An absent secret degrades, it never fails.
- Third-party actions are pinned to a commit SHA on purpose: they hold the signing and Play/Firebase credentials, and a floating `@v1` can be repointed upstream. Do not tidy them into tags; dependabot proposes bumps. GitHub's own `actions/*` stay on tags. The `github-actions` ecosystem scans `.github/workflows` and a *root* `action.yml` only, so `.github/dependabot.yml` lists `.github/actions/setup-android` under `directories` as well; drop it and that file's actions rot unseen.
- `versionName` is `git describe --tags --abbrev=0 --match "v[0-9]*"`. The filter is load-bearing (the repo carries non-release tags; builds once shipped `versionName = "pre-kmp"`), and `--abbrev=0` means it is always the bare tag, so `versionCode` is what names a build. Same filter in `/release`.
- A tag push does not ship. `uploadRelease.yml` uploads the AAB to the alpha track as a draft; publishing is manual in Play Console. A green workflow reached no one.
- `run:` blocks take secrets through `env:`, never `${{ }}` spliced into the script text. Validate workflow edits with `actionlint`.
- `trunk` protection has `enforce_admins: false` on purpose: direct pushes to `trunk` skip PR CI, and nothing runs locally before they land. `uploadApk` runs the full gate on every `trunk` push, so a bad direct push is caught after it lands, not before; with `required_linear_history` on and a single author, reverting it is cheap. Turning it on means every change needs a branch and PR. Change protection with a `PUT` of the whole object, never a PATCH. Check it: `gh api repos/emm3000/Just-Chill/branches/trunk/protection --jq '{checks: .required_status_checks.contexts, admins: .enforce_admins.enabled, linear: .required_linear_history.enabled, force: .allow_force_pushes.enabled}'`.
