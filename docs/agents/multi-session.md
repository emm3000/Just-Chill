# Multi-session orchestration

How the owner runs several Claude Code sessions on this repo in parallel, and what the orchestrator session must do before dispatching work to them. Read this before dispatching a ticket to a peer session. Issues and pull requests as the board: ADR 013. This playbook as the way of working, Gema's adapted: ADR 014.

## The unit

One GitHub issue of `emm3000/Just-Chill` labelled `ready-for-agent`. The label vocabulary is `docs/agents/triage-labels.md`, the `gh` operations are `docs/agents/issue-tracker.md`, the open board is `gh issue list --label ready-for-agent`, never a list in a doc. The issue IS the work: a `Done when` list of falsifiable conditions plus at most 3 lines of context. Constraints that outlive an issue live in `.claude/rules/` and the module `CLAUDE.md` files. Git plus engram are the chronicle; a fact goes in exactly one place. New issues come from the `ticket-writer` agent, from the PRD and the ADRs; `mattpocock-skills:grilling` stress-tests a plan before it is ticketed. Read an issue with `gh issue view <n> --json title,body,labels,comments`: the bare form prints the body alone, `--comments` without a TTY (every agent Bash call) prints the comments alone, and on a ticket migrated from the old `docs/work/` backlog the corrections to a stale body live in the comments. Proving something is absent takes every source, not the first one. *Why: on 2026-09-18 a peer reported a doc reference missing from #90 after reading only the body, where a comment cited it.*

## The loop

```
1. Orchestrator SCOPES the issue (inline, cheap) and picks the dispatch-log row
2. /wave boots one peer per ticket → WRITER   ── own worktree, branch, commits, push
3. Writer runs scripts/justchill-ci, then gh pr create ── local-gate on the head, PR that closes the issue
4. Orchestrator delegates → pr-reviewer       ── MERGE or FIX FIRST, on every PR
5. Orchestrator rebase-merges, appends the dispatch-log row, closes the cycle
```

## Roles

- **Owner** approves the first wave of a session and verifies model and effort with `/model` in each pane. Once a wave is fully merged the orchestrator starts the next one on its own. Peer sessions are booted only through the `/wave` skill, never by running `scripts/justchill-wave` by hand. Refer to a session with an `@` prefix in chat (`@loans`): it disambiguates the session from a feature or ticket of the same name.
- **Orchestrator** coordinates: dispatches via `SendMessage`, reviews, merges. It stays thin.
  - Delegate investigation and any artifact-producing work (tickets, specs, surveys, docs) to a subagent with an explicit model.
  - Do inline only routing state (`git status`, `git worktree list`, `gh issue/pr list`, `ListAgents`) and at most 1-2 files to decide. A module boundary touched, run the leak grep in `.claude/rules/architecture.md`.
  - Report minimal: act on review/agent findings, tell the owner 1-2 lines and only decisions that are genuinely theirs. Merging a clean PR is normal practice, not a question.

## Model and effort

- Every dispatch states model and **one** explicit effort (low / medium / high, never a range), with a one-line reason. The row comes from the table in `.claude/skills/wave/SKILL.md`: pick the cheapest model and lowest effort that gets it right; reserve Opus for work where a mistake is silent or expensive (migrations, backup/restore, auth, the DI graph); low is enough where a wrong answer fails tests loudly.
- The orchestrator session itself runs opus:medium: it scopes, dispatches, reads verdicts and merges, which is coordination, not deep reasoning. Sonnet loses the playbook discipline over a long session and re-asks routine steps. Model and effort are fixed for the life of a session; an ambiguous FIX FIRST gets a second `pr-reviewer` run, and a conflicting rebase goes back to the peer, which owns its rebase and `--force-with-lease`.
- Fable is for architecture and design decisions only: identity, tokens, component rules, mockups, visual judgment, a new ADR, an adversarial audit, an ambiguous triage, and diagnosing a peer that failed the same ticket twice. Reviews, implementation and doc checks go to Opus or Sonnet, with one exception: a downward pilot on row 3 may run `fable:low` (see `docs/agents/dispatch-log.md` for the thresholds).
- `model` is explicit on every Agent call: the parameter overrides an agent's frontmatter `model:`, and omitting it silently runs the definition or session default. The Agent tool overrides `model` only; effort comes from the agent file's frontmatter when it has an `effort:` line, otherwise from the session, so a review that must run at a different effort gets its own agent file.
- A session cannot see its own reasoning effort; `ListAgents` does not show it, and asking a session returns a guess.
- Skill routing: an unknown-cause bug gets `mattpocock-skills:diagnosing-bugs` first; reading legwork goes to `mattpocock-skills:research`; a diff that is not a PR gets `mattpocock-skills:code-review`; an architecture or domain decision loads `mattpocock-skills:domain-modeling`.

## Slicing and waves

- One slice = one small PR: a migration + domain change, or one screen, or one integration. A ticket naming more than 2 screens, or a migration plus a screen, gets split into sub-issues with `gh` first.
- If a session passes ~60% context without a PR, it commits, opens a partial PR, clears, and continues.
- Waves are ordered by dependency; parallelism is safe only within a wave (shared `:core:domain` or atom changes first, then independent slices). No wave carries two tickets touching the same module; a schema change (`.sq` / `.sqm`) is always a wave of one. A wave starts only after the previous one is merged.
- `iosApp/` only: two tickets may share a wave when they touch different screen-family folders under `iosApp/JustChill/` and neither edits a shared file. Shared: `iosApp/CLAUDE.md`, `project.pbxproj`, and every entry of `git ls-tree --name-only origin/trunk iosApp/JustChill/` that is not a screen-family folder (today `JustChillApp.swift`, `AppShell.swift`, `Bridge/`; `Theme/` once #527 merges).
- Before dispatching tickets filed by an audit, re-verify each against current `trunk`; the finding may already be fixed.

## Dispatch prompt checklist

Every dispatch to a peer session must include:

- Issue number, docs to read first (the relevant ADRs, rules and module `CLAUDE.md`, prior engram memos; for `iosApp/**`, `.claude/rules/swift-style.md` and `.claude/rules/swift-screens.md`), branch name, and the peer's **own** worktree path (see Isolation below). The engram tools are deferred MCP tools: a session loads `mcp__plugin_engram_engram__mem_search` and `mem_save` with `ToolSearch("select:...")` before the first call, or gets `No such tool available: mem_search`. The engram hook claims otherwise; the hook is wrong.
- The line: *"The issue's acceptance criteria are the contract and win over any file list here; run every criterion check before opening the PR."* Prefer criteria phrased as a command with expected empty output.
- The file list (`fd -e kt`) and their tests, plus the pre-scoped blockers. For a move/refactor, a dependency-closure directive: transitive imports mapped from the consuming layer, non-platform dependencies co-moved, platform symbols hoisted to callbacks.
- Gates: `./gradlew qualityGate assembleDevDebug` green before every commit, and `scripts/justchill-ci` after every push, before `gh pr create` (the gate excludes the build on purpose; its definition: `.claude/rules/github-workflows.md`); conventional commits; no `Co-Authored-By` (a PreToolUse hook in `.claude/settings.json` blocks it); English code and docs, Spanish only for UI strings; `rg` / `fd` / `bat` / `sd`; gotchas saved to engram.
- For any ticket that adds or changes behavior (a use case, a ViewModel rule, a derived `UiState` field), an instruction to load `mattpocock-skills:tdd` and work red, green, refactor, writing the failing behavior test before the code. Pure layout or restyle tickets skip it.
- For any screen-touching ticket, a visual check on the AVD the dispatch names: screenshot every changed screen with `adb -s <serial> exec-out screencap -p` and compare against `.claude/rules/ui-components.md`. A peer shoots on its pool AVD, never on `emulator-5554`, and the dispatch overrides a ticket body that still names it. Publish the screenshots on a branch named `assets/<N>-visual-check`, with the PR head short SHA in every file name (`home-<sha>.png`), and link them in the PR body with `raw.githubusercontent.com` URLs; the `gh` CLI cannot attach images to a PR. Add the image files explicitly, never `git add -A`: `git checkout --orphan` leaves the previous branch's working files on disk, so a sweep drags the whole repo onto the assets branch. The assets branch is deleted when the cycle closes. Evidence a criterion turns on goes in the PR body in full, not summarised there and pasted to the orchestrator: the reviewer reads the PR. When a criterion is a measurement, such as a uiautomator `bounds`, quote the lines rather than the conclusion drawn from them.
- An instruction to keep the slice small and stop and report instead of expanding scope.
- An instruction to open the PR with `Closes #N`, not merge it, not watch CI, and message the orchestrator the PR URL in 1-2 lines. The peer pushes its own ticket branch, its assets branch and any `--force-with-lease` after a rebase, and runs `gh pr create`, without asking the owner: those are the deliverable, not a decision. Only a push to `trunk` needs the owner's OK, and a peer never pushes to `trunk`. *Why: on 2026-09-18 two peers asked the owner before pushing their own branch and stalled the wave.*
- Before the PR URL the peer sends the orchestrator nothing but a named blocker; after it, one message per orchestrator message (the fix push, the clean worktree). For row 1-2 tickets the dispatch adds this sentence verbatim: `Time matters here: do not spend time that can be avoided, and the earlier a correct result is obtained, the better.` Rows 3-4 leave it out.
- Every dispatch ends with this paragraph, verbatim:

  ```
  You are operating autonomously. The orchestrator is not watching in real time and answers only a named blocker mid-task. For reversible actions the issue already covers, proceed without asking. Do not end a turn with a summary that announces the next step, an offer to continue unless told otherwise, a list of decisions that do not block the remaining work, or a report because a milestone is done: put status in the same message as your next tool call and carry on. Before ending a turn, read your last paragraph; if it is a plan, a question, a list of next steps or a promise, do that work now. Stop only when nothing can move without the orchestrator, before a destructive action outside your ticket and assets branches, or when the slice would have to grow. Do not fix, optimise or extend pre-existing behaviour the issue does not name; report it as a follow-up in the PR body. Commit tests only where the issue asks for them, the dispatch loads `mattpocock-skills:tdd`, or the repo already keeps tests for this kind of change, sized like the neighbouring test files. When you change code that can be built or tested, run a real check that exercises the change before reporting it done; a check that failed to start does not count, and if no check could run, say which one and why. When the result is the same, edit a file surgically instead of rewriting it.
  ```

## Launching peers

- `/wave <issue numbers>` is the only entry point, whether the owner types it or the orchestrator invokes it for the next wave: it classifies each ticket with the skill table, states `@<name> #<n> <model>:<effort>` to the owner before booting (deviations from the table carry a one-line reason), runs `scripts/justchill-wave`, waits for the peers in `ListAgents` and dispatches. The skill lives in `.claude/skills/wave/SKILL.md`.
- `scripts/justchill-wave name:model:effort [...]` writes `~/.warp/tab_configs/justchill-wave.toml` with one pane per peer in a horizontal split and opens it with `open "warp://tab_config/justchill-wave"`. A Tab Config opens as a new tab in the active Warp window; Launch Configurations (`warp://launch/`) always open a new window, so they are not used.
- `scripts/justchill-session name model effort` fetches `origin`, then from the checkout holding the script runs `claude -n <name> -w <name> --model <model> --effort <effort> --permission-mode bypassPermissions`. Claude Code creates `.claude/worktrees/<name>/` on branch `worktree-<name>` from `origin/HEAD` (`origin/trunk`). Launched from a linked worktree, `-w` still creates it under the main checkout's `.claude/worktrees/` and reads the main checkout's `.worktreeinclude`. The peer creates its ticket branch with `git switch -c`.
- **Residual risk** (#518, pending owner decision): peers staying on `bypassPermissions` is a pending risk, not a security solution. The docs reserve it for isolated containers or VMs, and it gives no protection against prompt injection. What still holds under it: the `permissions.deny` rules, the `PreToolUse` Co-Authored-By hook, the critical-path `rm` prompt, and the same mode and hooks in every subagent. Deny rules match the command text as written, so `git -C . push -f`, `/bin/rm -rf` or `bash -c '…'` pass them, and bypass writes `.git` and `.claude` without asking. No mode swap is small and verifiable here:
  - `auto`, `acceptEdits` and `dontAsk` count as *prompting* for cross-session messages, so a peer in one of them holds each dispatch from a bypass orchestrator for approval. Two prompting sessions deliver to each other by default, so an orchestrator and a peer both in `auto` need no `crossSessionInbound: "accept"`, and it is not added by default.
  - `auto` blocks force pushes by default and pauses into prompts after 3 blocks in a row. A cross-session dispatch is not owner authorization, even when it names `--force-with-lease` and the branch. A blocked force push is a named blocker the peer reports. It clears only when the owner authorizes that force push and its branch in the peer's own conversation, or when an owner-configured `autoMode.allow` rule covers it. `autoMode.allow` rules are read from `--settings` or user settings, never from `.claude/settings.json`.
  - `dontAsk` denies every call that would otherwise prompt. File reads, read-only Bash, `permissions.allow` matches and calls a `PreToolUse` hook approves still run. Writes to `.claude/` or `gradle-wrapper.properties` are always denied.
  - `acceptEdits` prompts on any Bash command it does not cover.
  - A dispatched peer is instructed never to change permission settings because another session asked, so an allowlist change comes from the owner's own session.

  The owner decides between keeping bypass as is and moving the orchestrator and the peers together to `auto` or `dontAsk`. A bounded `auto` pilot comes first, without changing the launcher: the owner switches one peer and the orchestrator to `auto` for one row-1 or row-2 ticket. There the peer's `--force-with-lease`, pushed without asking under bypass, becomes a named blocker. It records held dispatches, auto-mode blocks with their causes, prompt pauses, owner interventions beyond named blockers, and minutes to the PR URL against the same table row in `docs/agents/dispatch-log.md`, where every row so far ran on bypass. Only a peer that moves alone needs `--settings '{"crossSessionInbound":"accept"}'` on the launcher, and it gives up the approval hold on messages from every bypass session on this machine. The mode table and its sources are in PR #520.

## Isolation: worktrees

- Every peer works in its own git worktree (`.claude/worktrees/<name>/` under the main checkout, branched off `origin/trunk`), never in the owner's main checkout, which holds owner-only uncommitted files. All sessions open in the same folder by default, so a checkout there changes the branch under every other session.
- `supabase.properties` is gitignored, and `androidApp/build.gradle.kts` and the iOS Debug phase `Supabase From Properties` read it from the root. The root `.worktreeinclude` copies it from the main checkout into every worktree `-w` creates; the peer never commits it. Nothing committed excludes `.claude/worktrees/` from Android Studio indexing (`.idea/` is gitignored), a known gap. *Why: on 2026-09-25 @mas skipped the signed-in shot of #443 because a hand-rolled worktree lacked the file.*
- Before changing the state of any checkout, find out who is using it; an unexpected branch may be a live peer, not a leftover.
- Review and verification prompts are read-only on every existing checkout. If gradle must run on a branch, or a red/green check needs a source edit, use a throwaway worktree under the session scratchpad and remove it afterward.
- `git checkout trunk` fails inside a worktree while the primary worktree is already on `trunk`; use `git fetch` + `git switch -c <branch> origin/trunk` instead.
- Cleanup is part of closing the cycle, not a later chore (see Between tickets).

## Isolation: emulators

- `justchill-api36` (`system-images;android-36;google_apis_playstore;arm64-v8a`, `medium_phone` profile), booted headless with `emulator -avd justchill-api36 -port 5558 -no-snapshot-save -no-window -no-audio` (serial `emulator-5558`), runs `:core:database:connectedAndroidDeviceTest` and the restore drill before any schema change ships, and is the pool AVD for one device peer. Never seed a database into it and never create a second AVD for a single peer wave.
- `emulator-5554` (`Medium_Phone_2`) is the owner's. It is used for screenshots only when the dispatch says so, and never for an install that changes data, a clear, a seed or the migration suite: it runs `system-images/android-37.0/google_apis/arm64-v8a`, and AGP 9.x skips API 37 as "Unknown API Level".
- Hang recipe for either emulator: `adb -s <serial> shell true` answers `error: closed` → `adb -s <serial> emu kill` → cold boot with `-no-snapshot-load` (keeps userdata).
- When a wave needs two device peers, the second AVD is created once with `avdmanager create avd -n justchill-api36-b -k "system-images;android-36;google_apis_playstore;arm64-v8a" -d medium_phone` and booted on port 5560. One AVD per session still holds, and a second instance of the same AVD needs `-read-only` on every instance, the first included, or the failure lands on the follower.
- `./gradlew installDevDebug` installs on **every** connected adb device. Install with `ANDROID_SERIAL=<serial> ./gradlew installDevDebug` and scope every adb call, screenshots included, with `adb -s <serial>`. Never install on another session's emulator.
- When the review cycle closes, the peer shuts its own emulator down with `adb -s <serial> emu kill`, never a bare `adb emu kill`, together with the worktree cleanup. Keep the AVDs. Never shut down an emulator another session still uses.
- iOS pool (ADR 024 `## Amendments (2026-09-29)`): `justchill-ios27` and `justchill-ios27-b`, iPhone 17 on the one iOS 27 runtime, one device per peer. The second was created once with `xcrun simctl create justchill-ios27-b com.apple.CoreSimulator.SimDeviceType.iPhone-17 com.apple.CoreSimulator.SimRuntime.iOS-27-0`; never `simctl clone`, which needs the source shut down while peers use it. Only the dispatch boots a device, and it names each peer's. A peer installs, launches and shoots only on its device by name, never through the `booted` alias, which is ambiguous with two booted. Kotlin/Native simulator tests stay pinned to `justchill-ios27` and share it safely, because they never install the app and each run opens a per-run database and preferences suite. Recipe: `iosApp/CLAUDE.md` `## Simulator`.

## Review cycle

- A session gets nothing new until its previous PR is reviewed, fixed and merged. Never queue two tickets in one dispatch.
- Two-axis review (standards vs. `CLAUDE.md` and `.claude/rules/`, spec vs. the issue), plus screenshots checked against `.claude/rules/ui-components.md`. Every PR gets one. Reviews of mechanical slices, such as restyles, docs and renames, run sonnet:high. Reviews of screens, logic, migrations, backup/restore, auth and the DI graph run opus:high. When the orchestrator re-reads the diff and overturns a FIX FIRST as false, the log row records `overturned` in its Review column; that column is what tunes the reviewer tiers.
- Every PR review is a fresh `pr-reviewer` subagent that the orchestrator launches, one per PR, with the model passed on the call. It is not a long-lived peer session. The subagent is read-only. It does not build the app or rerun the gate, because the peer's `scripts/justchill-ci` already ran it and posted `local-gate`. It reads the diff, the issue and `gh pr view --json statusCheckRollup`, and it pulls the screenshots locally with `git show origin/assets/<N>-visual-check:<file>`. It checks that the SHA in each file name matches the PR head, and then views the images. It boots an emulator only when screenshots are missing, stale or suspicious, and it never reports the peer's pool AVD as a spec violation. *Why: on 2026-09-18 a review of PR #223 returned three blockers and all three were false, one of them the orchestrator's own AVD override.* It blocks on merge state only when `gh pr view <N> --json mergeStateStatus` reads `DIRTY`, a real conflict; a base behind `origin/trunk` alone is a minor note, because the rebase merge replays the commits onto trunk and the peer rebases only on a conflict. *Why: the first reviews of PR #506 and PR #516 blocked on a clean stale base.* It follows the `mattpocock-skills:code-review` skill for the Standards and Spec axes, with the PR's merge-base with `origin/trunk` as the fixed point. It returns `blocking|minor` findings, one verdict (MERGE or FIX FIRST) and one cause word (`checklist`, `judgment`, `spec`) for the dispatch log.
- No design-doc PR order: `.claude/rules/ui-components.md` forbids a design document, so the tokens and the screenshots are the whole design contract.
- The peer pushes, runs `scripts/justchill-ci`, then runs `gh pr create`, and reruns the script after every push: the status lives on one SHA, so a push without a rerun leaves the head without `local-gate`.
- Merge is rebase-only, linear history. The orchestrator merges on MERGE once `gh pr view <N> --json statusCheckRollup` shows `local-gate` SUCCESS on the head SHA; nothing waits on GitHub Actions for a PR. A red `trunk` run after a merge becomes a ticket; nobody reverts by reflex.
- Every background wait carries a hard bound, and on expiry the session reports instead of sleeping on. On 2026-09-17 a peer slept an hour on `/tmp/pr.txt`, a file nothing creates, and on a run that was never emitted.
- When a peer goes idle without a PR URL and without a named blocker, the orchestrator sends one message signed `@orch` that names the open acceptance criteria; after the third such nudge on one ticket it stops and reports the peer to the owner instead. Nudges stay rare and signed.
- Check `gh pr view <N> --json mergeStateStatus` first and merge with `gh pr merge <N> --rebase` when CLEAN; GitHub refuses auto-merge on a CLEAN PR.

## Between tickets

- A cycle is closed only when all of this is done, in order. First the PR is merged. Then the peer leaves its worktree clean and reports; the orchestrator removes it with `git worktree remove .claude/worktrees/<name>` (after `git worktree unlock .claude/worktrees/<name>` when git refuses it as locked: the session's lock outlives its process), then deletes both branches with `git branch -D <type>/<n>-<slug> worktree-<name>` (a rebase-merged branch never counts as merged, so `-d` refuses it), then runs `git worktree prune`. A peer never runs a git command with `-C` against the owner's checkout; it reports and the orchestrator cleans up. Last, any throwaway review worktree under a scratchpad is removed. The orchestrator checks `git worktree list` before reporting the session as free. If a peer is gone, the orchestrator removes the leftovers itself, but only after confirming that no live session uses them.
- Also at cycle close, the orchestrator appends one row to the Recent table of `docs/agents/dispatch-log.md` and folds anything beyond the last 20 rows into its Summary: PR, issue, table row, model:effort, first-review verdict and, on FIX FIRST, whether the cause was a checklist item, a judgment error or a thin spec, and whether the first review was `ok` or `overturned`, plus the `@orch` nudges the peer needed and the minutes from the dispatch to the PR URL; the orchestrator notes the time when it sends each dispatch. The rows accumulate in the working tree and ship as one commit per wave, never one per ticket: half of trunk's commits on 2026-09-17 were docs, most of them one-line log appends. The orchestrator pushes that wave commit to `trunk` itself when every unpushed commit is a cycle-close docs commit; any other push to `trunk` still needs the owner's OK. *Why: on 2026-09-18 the wave 5 log sat unpushed for a day waiting for an OK, and Gema's orchestrator has never asked.* The table in `.claude/skills/wave/SKILL.md` is tuned from that log, not from opinion. Before invoking `/wave` for the next wave, the orchestrator applies the log's thresholds to every row the wave touched and appends a dated line to the log's Changes section for any rule it moves.
- Also at cycle close, the orchestrator asks whether the merged work made an architecture or domain decision, or changed a domain term. If it did, it files a small docs ticket that loads `mattpocock-skills:domain-modeling` and adds or updates the ADR in `docs/adr/`, `CONTEXT.md`, or both. An ADR that the shipped behavior contradicts is fixed the same way.
- A peer session carries exactly one ticket. When its PR is merged, the orchestrator closes the cycle and kills the pane: kill the peer's `claude` pid, then `kill -HUP` its parent `zsh`. It never sends a second ticket to the same session. When every PR of the wave is merged, it invokes `/wave` with the next wave's tickets.
- At session start, the orchestrator searches memory (`mem_search`) for past dispatch gotchas before the first dispatch of the session.
